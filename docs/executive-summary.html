The organizer's format rule is “data outside the bounds is null or nan” and “a single layer of float32 values between 0 and 1” (page 967). NaN is the literal reading, it is what sample_submission.tif itself uses, and it is what five of the owner-reported scored artifacts in registry/live_scores.json use (0.1855, 0.1922, 0.2449, 0.2477, 0.2600) — so NaN-outside is demonstrably accepted and scored.

A predicted 0 outside the footprint is also harmless to the score, because p = 0 contributes nothing to either penalty term, and it is immune to any uploader that coerces NaN into a sentinel. That is the only reason the zeros twin exists. Why the Predicted values must be in range [0, 1] error happens, and why it cannot come from this file

That validator message has three realistic causes:

  1. NaN or Inf inside the footprint. A NaN comparison is false, so a NaN pixel fails a 0 ≤ p ≤ 1 test even though it is not “out of range”. This file has 0 non-finite pixels inside the footprint.
  2. A float32 NoData sentinel left in the data. The competition's own training_features.tif uses -3.4028234663852886e+38; if a submission inherits it, the validator sees a hugely negative value. This file's in-footprint range is [0.0, 1.0].
  3. Values above 1 from writing a probability that was never clipped, or writing a count. Both twins are strictly binary {0.0, 1.0}.

Independently of the pipeline, scripts/validate_submission.py re-opens each written file and checks all of the above plus CRS, band count, dtype, dimensions, geotransform equality with the template, outside-footprint encoding and NoData. Both twins report PASS on all 12 checks.

What was built, in one paragraph

Seven detectors target the population the metric actually scores — fault pixels the USGS/INGENIOUS catalogue does not contain, which staff confirmed is what “new fault” means and that catalogue pixels are masked pixel-exactly in both rounds. They are fused by geometric mean so a pixel must be supported by several independent factors, then emitted as a best-first Poisson-disk dot field at 2.8 px spacing with every pixel within 2 px of the catalogue excluded. The number of dots is not inherited from a previous artifact: emission stops where the measured marginal hit rate, transferred to the live scale by the anchor artifact's instrument/live ratio of 0.451, crosses the break-even price π* = 3.149% derived from the calibrated |G| = 14,143. Promotion required a Wald SPRT decision at pre-declared α=0.05, β=0.1 over 32 spatially separated folds, plus a leakage gate at 2%.

Remaining work and what blocks success

  1. Only one live data point anchors the transfer factor. A second independent nested pair of scored artifacts would tighten it. None is available offline.
  2. Sparse external coverage. 879 QC'd heat-flow wells over 51,674 km² and 1,244 geothermometer values are thin; the interpolations are two-scale Gaussian-weighted local means, not kriging.
  3. 3 submissions per rolling 7 days caps how fast the pricing model can be validated live.
  4. Phase 1 selection is blind and binding. One submission must be chosen for both the Initial Prize Round (private set) and the Final Prize Round (labels expanded by expert review of all Phase 1 submissions). Staff: predictions “have an impact on final evaluation even if they are not the most performant in Phase 1” — so geological defensibility is a design input, not decoration.
  5. No hidden labels. Both instruments are proxies. I2 is prevalence-matched to the calibrated |G|, which removes the ~4× inflation but does not make SGMC faults the scored population.
  6. qc_code ‘G’ heat-flow wells are excluded on distributional grounds (median 218 vs 85 mW/m², max 10,234 mW/m²). That is a judgement call documented in external.load_heat_flow, not a rule from the release documentation, which could not be reached from this sandbox.
