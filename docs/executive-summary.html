The six clicks

  1. Download. Click here — or the ZIP if the browser uploader misbehaves. Both contain the identical GeoTIFF.
  2. Sign in at the competition submissions page and press New submission.
  3. File to submit → Choose file. Select the .tif you downloaded (or the .zip).
  4. Note (optional). Paste this, so you can tell it apart later — 193 of the 200 characters allowed: 
    GEMSDOE39 H39-A R39A | blocked-OOF off-catalogue discriminant, OOF AUC 0.661; holdout lift 0.670 vs 0.274 control; SPRT 9/9 accept-H1; 24,000 dots, NN 3.0 px, none within 200 m of the catalogue
  5. Create submission. Scoring is automatic and takes a few minutes. One submission per name; we suggest GEMSDOE39-H39A-R39A.
  6. Record what comes back. Paste the returned score into registry/score_ledger.csv in this repository. That is what turns the next round's guess into a measurement.
Submission limits. The rules cap submissions per team per week, and one file is used for both prize rounds — the Final Prize Round re-scores that same file against an expanded label set. Do not treat the public leaderboard number as the prize result.

Why this file and not another one

Three things had to be true before we generated it, and all three are checkable:

  1. It beats the incumbent on a holdout, by a declared sequential test. Against a topographic × magnetic control (mean lift 0.2735), the H39-A field scores 0.6698. The test is a sequential probability ratio test with α = 0.05, β = 0.10, p₀ = 0.50, p₁ = 0.70 and anytime-valid boundaries upper = log(1/α) = +2.9957, lower = log(β) = −2.3026. It consumed 9 of 12 cells and stopped on its own at LLR = +3.028 → accept H1. We did not keep feeding it cells after the boundary was crossed, and we report all five candidates, not just the winner.
  2. Its pixel budget comes from the metric's own break-even rule, not from taste. Adding one pixel with expected kernel credit w changes the DTI denominator by exactly 0.2, so a pixel pays iff w > 0.2·DTI. Fitting TP = A·nγ to the only clean within-lineage pair in the historical record and imposing that condition gives break-even budgets of 5,400–26,800 px depending on the assumed truth size, with the DTI surface nearly flat across 13,000–45,000 px. We ship at 24,000.
  3. It is not a copy. Compared against 241 retrievable same-grid rasters from the sibling GEMSDOE repositories: maximum Jaccard overlap 0.0240, maximum containment against a non-degenerate reference 0.1780, maximum |Pearson r| 0.0547. Full table in registry/uniqueness.json.

The Predicted values must be in range [0, 1] error — both causes

This rejection has two distinct origins, and they need two different fixes. We removed both.

Cause 1 — the float32 nodata sentinel

The supplied training_features.tif encodes no-data as -3.4028234663852886e+38. If that value is carried into a prediction raster, roughly 7.1 million cells land far outside [0, 1] and the portal rejects the file. Our writer clips and validates every cell before writing and refuses to emit anything outside the range.

Cause 2 — NaN outside the footprint

The problem page says data outside the bounds is "null or nan", and the sample submission does use NaN. But a NaN-carrying raster with nodata=NaN is one validator change away from the same rejection.

The fix we ship

The recommended file is all-finite: real predictions inside the footprint, 0.0 outside, no NaN anywhere, and no nodata tag at all. There is no sentinel of any kind for a validator to trip over. We verified this by re-opening the written bytes, not by trusting the writer:

What we do not know

  • The score. We have no DrivenData credentials, so no number on this site is an organizer score. Every figure is either measured locally from the rasters or quoted with a link.
  • Whether the field or the budget is binding. At a fixed budget, DTI is nearly linear in true positives, so field quality dominates. But no local instrument ranks fields: against the 30 owner-reported live scores our best proxies sit at Spearman ρ between −0.37 and +0.09, none significant. The SPRT validates against hidden catalogue faults, which is a proxy for the real hidden set rather than the real hidden set.
  • The 0.2778 attribution. The project brief credits 0.2778 to h33-h33-2-b2-…-e5eb6e7e-zeros, but the GEMSDOE32 site marks that file "UNSCORED" and the public board shows a 0.2778 row with no filename. We treat it as an official board row, not a verified score for that file.
Do not confuse the three leaderboards. The public board scores a public chunk of the new faults. The Initial Prize Round scores a private chunk. The Final Prize Round re-scores the same uploaded file against an expanded label set that includes faults experts verify after reading everyone's submissions. A file tuned hard to the public number is not automatically tuned to the prize.
